# Установка и обновление

## Требования

- [Claude Code](https://claude.com/claude-code)
- `bash`, `tar` — на macOS и Linux есть из коробки; `curl` — только для
  проверки обновлений, без него она молча выходит
- Опционально `python3`: им установщик фильтрует MCP-сид, и им же хуки
  читают свой JSON, когда нет `jq`; нет ни того ни другого — `leak-guard`
  сканирует сырой payload, а запрещающие хуки пропускают вызов, так что без
  одного из двух они не сторожат
- Опционально `uvx` для засеянной serena, `npx` для context7, `node` и
  Playwright (`npx playwright install chromium`) для браузерного QA

Своего Keel не держит ничего: ни MCP-сервера, ни демона, ни индекса, который
надо строить. Ядро — это shell и markdown.

## Быстрый старт

**1.** Скачайте `keel_1.8.0.tgz` и `keel_1.8.0.tgz.sha256` из
[Releases](https://github.com/bogdanov-igor/keel/releases/latest) в папку
проекта.

**2.** Откройте проект в Claude Code и скажите:

> Установи keel из архива в этой папке: сверь sha256, распакуй, запусти
> `keel/install.sh` и расскажи, что появилось.

**3.** Жили под SkillForge — добавьте «почисти остатки старой системы и
предложи переаудит»: машинерия уедет в карантин, ничего не потеряв, см.
[миграцию](migration.md).

## Руками

Оба пути запускают один и тот же установщик.

### Из архива

```sh
cd /path/to/project                 # оба файла скопированы сюда
shasum -c keel_1.8.0.tgz.sha256     # сначала целостность: ждём "OK"
tar -xzf keel_1.8.0.tgz
bash keel/install.sh                # без аргумента = ставим в этот каталог
```

Папку `keel/` можно оставить в проекте (повторный запуск `install.sh`
обновит ядро, а проверка обновлений читает её `VERSION`) или удалить.
Оставляете — добавьте `keel/` и `.tgz` в `.gitignore`.

### Из репозитория-исходника

```sh
git clone https://github.com/bogdanov-igor/keel.git
bash keel/install.sh /path/to/project
```

## Что делает установщик

| Действие | Детали |
|---|---|
| Ставит ядро | Копирует `bundle/.claude` настоящим каталогом, никогда симлинком — симлинки ломают разрешение путей у хуков и память, привязанную к проекту. Существующий `.claude` сначала уезжает в `.claude.bak.<timestamp>`, и это имя делается уникальным, а не просто с меткой времени: две установки в одну секунду заставляли `mv` положить второй бэкап внутрь первого, и настоящий прежний `.claude` оказывался на два уровня глубже пути, который был назван в сообщении. Всем `*.sh` внутри нового `.claude` возвращается бит исполнения: распаковка и копирование его теряют, а хукам он нужен уже на следующем старте сессии. Скиллы, агенты и хуки, о числе которых он докладывает, считаются по только что установленному дереву, а не по числу в скрипте. |
| Штампует версию | Пишет `.claude/VERSION` — его читает проверка обновлений. |
| Сохраняет ваши скиллы | Каталог скилла, которого нет в поставке ядра, переносится из прежнего `.claude` — включая лежащий в старом `skills/_user/` от SkillForge. Если в бэкапе ядро SkillForge (маркер — `_protocol.md`), вашими считаются только скиллы из `_user/`, а его собственные остаются в бэкапе, чтобы машинерия предшественника не вернулась с переустановкой. |
| Переносит вашу обвязку Claude Code | `settings.local.json` (ваши разрешения), `commands/`, `rules/`, `output-styles/` и ваши агенты возвращаются пофайлово и только туда, где у ядра ничего нет, чтобы файл ядра не заслонила его же устаревшая копия. Агенты-персоны SkillForge — машинерия предшественника, они остаются в бэкапе. |
| Сеет состояние проекта | `memory/` с `lessons/`, `antipatterns/`, `patterns/` (в каждом `.gitkeep`, иначе пустые каталоги не переживут клон), `stages/`, `BACKLOG.md`, `PARKED.md`, `OPS.md`, `keel.json`, `memory/MEMORY.md` — только там, где их нет. Существующее не перезаписывается, и установщик говорит, что именно из двух случилось. |
| Держит четыре вещи вне git | Дописывает в `.gitignore` `.secrets.env`, `.qa/`, `.claude/worktrees/` и `.claude.bak.*`. Файлу без завершающего перевода строки он сначала дописывает его — один раз, до паттернов: слепое дописывание склеивает первый новый паттерн с последним старым и молча ломает оба. |
| Сеет `.worktreeinclude` | Одна строка, `.secrets.env`. Сессия `claude --worktree` стартует в свежем чекауте, где по определению нет игнорируемых файлов, так что без этой строки файла секретов, на который завязан весь проект, там просто нет. |
| Сеет MCP с фильтром | Пишет `.mcp.json`, только если в проекте его нет, и только те серверы, чей лаунчер на этой машине есть: serena нужен `uvx`, context7 — `npx`. Сервер, который не может стартовать, хуже отсутствующего — Claude Code дёргает его каждый старт сессии и докладывает об ошибке, которой вы не создавали, — поэтому про остальные пишется строка, откуда их скопировать, когда лаунчер появится. Существующий `.mcp.json` ваш, он остаётся ровно как есть, но его пересчитывают: каждый настроенный сервер тащит всю свою схему инструментов в каждую сессию и в каждый порождённый ею сабагент, и установщик говорит, сколько их, плюс слово, если serena среди них нет. |
| Сеет рекомендации VS Code | `.vscode/extensions.json` с Foam и превью mermaid — и только если у проекта нет своего файла рекомендаций. Память — это граф `[[wikilink]]`, а руководства рисуют в mermaid; из пустого редактора не видно ни того ни другого. |
| Докладывает интеграции | По строке на `gh`, `uvx`, `npx`, `node`, `python3`, `codex`, `gemini` и браузеры Playwright — есть они или нет, — плюс строка про Claude Design, который живёт в вашем аккаунте Claude и на диске не детектируется. Только детект: установщик, который сам ставит тулчейны и куда-то логинится, — это установщик, который вы не проверите. |
| Находит остатки | Гоняет миграционный свип в режиме превью и поднимает баннер `migrate`, когда нашлась настоящая машинерия. Отчёт, где только помеченные пути — например, тот самый `.claude.bak.*`, который создала эта же установка, — остатками не считается и баннер не поднимает. Ни один файл здесь не двигается. |
| Проверяет себя и откатывается | Контракт лежит в `.claude/CLAUDE.md`, каждый хук исполняемый, число установленных скиллов совпадает с тем, что поставляет бандл, из которого ставили (жёстко зашитое в скрипт число было второй описью того же самого: он говорил 37, когда бандл вёз больше, и наполовину скопированный бандл проходил мимо него), `scout` и `verifier` на месте, `settings.json` разбирается (синтаксическая ошибка там молча стоит проекту всех его хуков), и `anchors.sh` из `recall` реально запускается — на одноразовом проекте, потому что на настоящем инструмент вправе сообщить о находках, и это не поломка. При провале неудачное ядро удаляется, а прежний `.claude` возвращается из бэкапа сам: полуустановленное ядро там, где стояло рабочее, хуже несостоявшегося обновления, и помнить имя бэкапа вы не обязаны. |

В конце он печатает следующие шаги, и читаются они одинаково — запускали вы
или Claude: скилл `migrate`, если нашлись остатки; браузеры Playwright, если
нужен браузерный QA; открыть проект в Claude Code, если вы были в терминале.

### После установки

Запустите `/integrations` в первой же сессии: скилл проверяет, до чего этот
проект дотягивается, — CLI, браузеры Playwright, MCP-серверы, Claude Design,
модели для второго мнения, — задаёт по одному вопросу на пункт и пишет
ответы в реестр доступов в `OPS.md`, отложенное в `PARKED.md`, то, что нужно
поставить, — в `BACKLOG.md`. Ничего не ставит и никуда не логинится. Пока он
не отработал, каждая следующая сессия гадает.

`.secrets.env` установщик добавляет в `.gitignore` и называет в
`.worktreeinclude`, но не создаёт: его вы пишете руками. Настройки ядра
запрещают его чтение — на Claude Code 2.1.87 инструмент Read и `cat`
получают отказ, а `grep -r` из каталога нет, и более новые версии отказывают
ещё и в записи. В заметках, коде и артефактах значение пишется как
`{{secret:KEY}}`, а хук утечек запрещает запись со знакомым ему значением.

## Обновление

Самый простой путь: скачать новый архив в папку проекта и сказать:

> Обнови keel из архива в этой папке.

Руками — та же команда, что и установка, из более новой папки keel (свежий
релиз или `git pull`):

```sh
cd /path/to/project
bash keel/install.sh
```

Файлы ядра заменяются. Состояние проекта — память, стейджи, бэклог,
парковка, `OPS.md` — не трогается, ваши добавления внутри `.claude/`
переезжают. Старые бэкапы `.claude.bak.*` можно спокойно удалять.

### Как вы узнаёте об обновлении

Хук на `SessionStart` сравнивает `.claude/VERSION` с копией ядра рядом
(папка `keel/` в проекте или `$KEEL_HOME`) и с последним [релизом на
GitHub](https://github.com/bogdanov-igor/keel/releases). Что-то строго новее
— одна строка, и в ней сказано, перезапустить ли установщик из папки рядом с
проектом или скачать релиз; версия актуальна — ни строки, и обычный случай
стоит ноль токенов.

Запрос к GitHub кэшируется на 24 часа при удачном ответе и на час при
неудачном, так что сессия в поезде или за фаерволом платит трёхсекундный
потолок curl один раз, а не на каждом старте. Без `XDG_CACHE_HOME` и `HOME`
кэшу негде жить: проверка релизов пропускается, локальные источники работают
дальше. Любой сбой — тихий выход, заблокировать сессию проверка не может.

| Переключатель | Действие |
|---|---|
| `update_check` в `keel.json` | `"enabled": false` выключает проверку для этого проекта; в том же блоке лежат `repo` и `interval_hours`. |
| `KEEL_NO_UPDATE_CHECK=1` | Хук выходит сразу. Для CI и машин без сети. |
| `KEEL_HOME` | Путь к репозиторию keel или распакованному ядру. Его `VERSION` сравнивается с установленной, так что собственная сборка объявляется как релиз. |
| `KEEL_SECRETS_FILE` | Откуда хук утечек читает значения секретов, если они лежат не в `.secrets.env` проекта. |

## Сборка архива (мейнтейнерам)

```sh
bash build-archive.sh    # → dist/keel_<version>.tgz + .sha256
```

Сам `build-archive.sh` в архив не кладётся. Сначала он проверяет по именам
все свои входные файлы, ещё до того как что-то запустится или скопируется:
`ROADMAP.md` въехал в архив в 1.8.0, фикстура самой сборки его не получила,
и провал вылез как `sha256: No such file` — ни файла, ни шага, которому он
был нужен. Потом `test/run.sh`: более 400 самотестов скриптов ядра, офлайн,
на одноразовых фикстурах, и сборки не будет, если хоть один упал. Затем
свежий архив распаковывается во временный каталог и по-настоящему ставится,
а результат сверяется от начала до конца: контракт, сиды, права на хуки и
скрипты, отметка версии, документация на обоих языках вместе с русской
диаграммой, лицензия, разбор `settings.json` и молчание проверки обновлений
на собственной версии. При провале рабочая область остаётся — для разбора.

Сборка герметична: свой кэш вместо настоящего `~/.cache`, никакой сети.
Архив я пакую не системным `tar`, а `python3` (`tarfile` + `gzip`): формат
ustar, записи в порядке байтов пути, uid/gid 0 и пустые имена владельцев,
права 0755 каталогам и исполняемым и 0644 остальным, время 2020-01-01 UTC,
gzip без имени и времени файла в потоке. Поэтому один и тот же тег даёт один
и тот же sha256 на любой машине — bsdtar и GNU tar по-разному набивают
восьмеричные поля заголовка. Распаковка — обычным `tar -xzf`.
